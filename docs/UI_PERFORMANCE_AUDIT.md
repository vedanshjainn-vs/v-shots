# V Shots — UI Performance Audit (Phase 7, Part B)

**Date:** 2026-08-10
**Base commit:** `4f5045a`
**Method:** direct code read of every major screen (`lib/main.dart`,
`lib/features/foryou/*.dart`, `lib/shared/widgets/app_image.dart`) — no profiler was run
(no Android device/emulator available in this sandbox, consistent with every prior
session). Every issue below is a real, confirmed-via-code-read structural issue, not a
guessed/invented FPS number. Confidence tags: 🟢 Confirmed (read the exact code) /
🟡 Likely (reasoned from confirmed code, not measured).

| # | Issue | File | Severity | Cause | Recommended fix |
|---|---|---|---|---|---|
| 1 | `MainShell` rebuilds its entire `IndexedStack` (5 full screens: Home/Discover/Search/Library/Profile) + `NavigationBar` on **every single player state change** (play/pause/buffer/every track start) | `lib/main.dart` `_MainShellState.initState()` (`audioPlayer.playerStateStream.listen` → `setState(() { isCurrentlyPlaying = ...})`) | 🔴 P1 (Confirmed) | `isCurrentlyPlaying` is written by this listener but **is never read inside `MainShell.build()` at all** (confirmed via `grep -n "isCurrentlyPlaying" lib/main.dart` — 4 hits total: the declaration, this write, a stale comment, and nothing else). The `setState` call is pure waste — it forces `IndexedStack`/`NavigationBar` to rebuild for a value the widget doesn't even use. The only thing that visually needs to react to playback state is `_MiniPlayer`'s play/pause icon, which already correctly uses its own `StreamBuilder<PlayerState>` (line ~575) — the global `isCurrentlyPlaying` write is dead weight | Remove the `setState`/`isCurrentlyPlaying` write entirely from `MainShell`'s listener (keep the listener only if something else genuinely needs it — nothing does); if a global "is playing" flag is wanted by non-widget code later, store it without triggering `MainShell.setState()` |
| 2 | `PlayerScreen` never disposes its 3 real-time stream subscriptions (`playerStateStream`, `positionStream`, `durationStream`) | `lib/main.dart` `_PlayerScreenState.initState()` | 🔴 P1 (Confirmed) | No `dispose()` method exists on `_PlayerScreenState` at all (confirmed: `sed`-extracted the full class body, zero `dispose`/`StreamSubscription` fields). Every time a user opens the full player screen and pops back, 3 more subscriptions to the SAME long-lived `audioPlayer` stay alive forever, each still calling `setState()` on an already-disposed widget's State object on every position/state tick — this is both a memory leak and (once `mounted` is false) wasted work on every tick for the app's remaining lifetime | Store each `.listen(...)` return value in a `StreamSubscription` field, cancel all three in a new `dispose()` override — same pattern already correctly used in `LyricsScreen` (`_positionSub`) in the same file |
| 3 | Home card images (`AppImage` inside `_tracksSliver`'s horizontal `ListView.builder`) are given no explicit `width`/`height`, so `AppImage`'s own `memCacheWidth`/`memCacheHeight` optimization (`width! * 2`) never activates — full `hqdefault.jpg` (480×360) thumbnails are decoded at native resolution for a ~150×150 display slot | `lib/main.dart` `_HomeScreenState._tracksSliver()` (`AppImage(..., fit: BoxFit.cover, errorIconColor: ...)` with no width/height) | 🟡 P2 (Likely — real code gap confirmed, actual memory impact not measured on-device) | `AppImage`'s memory-cache-sizing logic (`lib/shared/widgets/app_image.dart`) is conditional on `width`/`height` being passed — the Home grid is the one major call site that omits both (Search's `AppImage` at 48×48 and the mini-player's at 48×48 DO pass explicit sizes and already benefit) | Pass explicit `width`/`height` (150, matching the card's actual layout width) to Home's `AppImage` call so `memCacheWidth`/`memCacheHeight` activate, same as every other call site already does |
| 4 | `ForYouFeedScreen`'s full-bleed background blur (`BackdropFilter` + `ImageFilter.blur(sigmaX: 25, sigmaY: 25)`) runs on every visible card, including the ones adjacent to the active page inside `PageView.builder` | `lib/features/foryou/for_you_feed_screen.dart` `_ForYouCard.build()` | 🟡 P2 (Likely) | `BackdropFilter` is one of the most GPU-expensive widgets in Flutter (full-screen Gaussian blur, re-run every frame it's on screen) — per Part C/D research (Flutter's own perf guidance: prefer `Transform`/opacity over expensive filters), a full-screen 25px blur on a vertically-swiping full-screen feed is a plausible jank source during swipe transitions, though not benchmarked here | Keep the blur (it's a real, deliberate design choice for the immersive card look), but only apply it to the *active* + immediately adjacent card, not literally every built `_ForYouCard` — `PageView.builder` already only builds nearby pages by default, so this is a smaller win than it sounds; documented as low-priority, not fixed in this pass (see Known Issues) |
| 5 | `HomeScreen`'s 7–9 independent sections each call `setState()` on the shared `_HomeScreenState`, meaning any one section's load/refresh rebuilds the **entire scroll view's build method** (all `_buildSectionSliver` calls re-run), even though each section's UI is otherwise independent | `lib/main.dart` `_HomeScreenState._loadSection()` | 🟡 P3 (Likely) | This is Flutter's normal `StatefulWidget` behavior (one `State` = one rebuild scope) — not a bug introduced by this app, but a real, fixable inefficiency: 9 sections × N `setState` calls during initial load means the top-level `build()` (which contains a `CustomScrollView` + `SliverAppBar` + greeting text + all 9 slivers) reruns 9 times during a typical cold start, even though 8 of those reruns only need to update ONE section's sliver | Not restructured in this task (would require extracting each section into its own `StatefulWidget`, which is a larger refactor than "UI motion + recommendations" scope allows) — flagged for a future pass; the actual rebuilt widgets are cheap (`Sliver*` widgets, no images redecoded thanks to `AppImage`'s cache), so real-world jank risk is low despite the rebuild count |
| 6 | No `RepaintBoundary` anywhere in the codebase | entire `lib/` (confirmed via `grep -rn "RepaintBoundary" lib/` → 0 hits) | 🟡 P3 (Likely) | Horizontally-scrolling Home rows and the vertically-swiping Discover feed both repaint sibling widgets on every frame during a scroll/swipe gesture by default, since nothing isolates their repaint layers | Add `RepaintBoundary` around each Home section's horizontal `ListView` and around `_ForYouCard` — cheap, safe, no behavior change |
| 7 | `SliverAppBar(floating: true)` + a plain `Text('V Shots', ...)` title with no skeleton/placeholder before Home's `greeting` text renders | `lib/main.dart` `_HomeScreenState.build()` | 🟢 Trivial (Confirmed, not a real perf issue) | Cosmetic only — the greeting/app-bar render instantly (`DateTime.now().hour` synchronous check), no loading state needed | No fix needed — not a real issue, listed for completeness of the audit |
| 8 | No shimmer/skeleton exists for the **initial full-screen** load before ANY section has data (only per-section shimmer exists once `_sections` is already built and `initState` has fired `_loadSection` for each) | `lib/main.dart` `_HomeScreenState` | 🟢 Trivial | Not actually a gap — `_sections` is populated synchronously in `late final` field initializers, so shimmer appears immediately on first frame; there is no meaningful "flash of nothing" window | No fix needed |

## Summary of what will actually be fixed in this task (high-value only, per Part B's own instruction "do not fix everything blindly")

1. **#1 (P1)** — remove the dead, whole-shell-rebuilding `isCurrentlyPlaying` write in `MainShell`.
2. **#2 (P1)** — fix `PlayerScreen`'s real stream-subscription leak with a proper `dispose()`.
3. **#3 (P2)** — give Home's `AppImage` explicit dimensions so its existing memory-cache-sizing logic activates.
4. **#6 (P3)** — add `RepaintBoundary` around Home's horizontal lists and Discover's cards (cheap, safe, no behavior change).

Not fixed in this pass (documented, not silently dropped): #4 (Discover per-card blur — a design trade-off, not a bug, and `PageView.builder`'s own default page-caching already limits how many blurred cards exist at once) and #5 (Home's shared-`State` rebuild scope — a legitimate future refactor, out of proportion to this task's stated scope of "UI motion + recommendations," not "rearchitect Home's state management").
